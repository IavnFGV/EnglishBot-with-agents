Сделай минимальное, но полное изменение в EnglishBot, чтобы поверх текущей workspace/access модели появился простой стартовый admin facade для семейного использования без обязательного invite/join onboarding.

Контекст продукта:

- Текущая модель доступа уже сложнее, чем нужен стартовый UX.
- Под капотом можно сохранять текущие `workspaces`, `workspace_members`, teacher/student роли, publish и assignment-модель.
- Но на фасаде нужно убрать лишний геморрой для маленького сценария типа: я, жена, ребенок.
- На этом этапе это не продакшен: допустим один захардкоженный Telegram user id супер-админа.

Работай по правилам репозитория из `AGENTS.md`:

- Сначала держи изменение как можно уже.
- Читай только нужные файлы по `docs/module-map.md`.
- Не расширяй архитектуру без необходимости.
- Все bot-facing тексты через `englishbot/i18n.py`.
- Любую новую команду сначала добавь в `englishbot/command_registry.py`.
- После изменений обнови `CHANGELOG.md`, `context/current-state.md` и `.env.example`, если появится новый env var.

Цель фасада:

- Должен существовать один простой admin-only вход в UI.
- Доступ в него по одному захардкоженному Telegram user id, который можно сначала взять из `.env`, например `ENGLISHBOT_ADMIN_TELEGRAM_USER_ID`.
- Через этот UI админ может видеть уже зарегистрированных пользователей и быстро менять им права/участие без invite-кодов.
- Invite/join не удалять: просто добавить возможность это временно скипнуть.

Желаемое поведение:

- Любой новый пользователь по умолчанию считается `student`.
- Для каждого пользователя можно без боли подготовить стартовое окружение:
  - его personal teacher workspace, если он потом станет teacher
  - его personal student workspace, чтобы модель оставалась совместимой
- Админ может:
  - назначить пользователя teacher role
  - оставить пользователя student only
  - включить пользователя в нужные student workspaces
  - быстро собрать простую семейную конфигурацию без ручных invite/join
- Фасад должен позволять жить в модели, где человек:
  - изначально student
  - потом получает также teacher role
  - после этого может назначать homework/topic access другим участникам
- Ничего не ломай в текущей publish/assignment модели: просто сделай удобный bootstrap/admin path поверх неё.

Важно по продуктовой трактовке:

- Не пытайся сейчас строить идеальную enterprise-модель ролей.
- Нужен удобный стартовый фасад для “маленькой семьи/маленькой команды”.
- Нормально, если один человек может быть и student, и teacher в разных контекстах.
- Если текущая глобальная роль `user_profiles.role` мешает этому, предложи и реализуй минимальный совместимый путь, который не ломает текущие команды.
- Если совсем безболезненно dual-role не получается, допустим pragmatic compromise:
  - глобально user может быть teacher
  - но при этом оставаться участником student workspaces как student runtime participant
- Главное: на фасаде не должно требоваться понимать внутреннюю сложность модели.

Ожидаемый scope:

- Добавь один новый admin command, например `/admin_access` или `/admin`.
- Сделай очень простой Telegram UI:
  - список зарегистрированных пользователей
  - выбор пользователя
  - действия типа:
    - “make teacher”
    - “keep student”
    - “create default spaces”
    - “link into shared family/student space”
- UI может быть простым, но не спамным: придерживайся правила одного logical screen на одно сообщение.
- Предпочти `aiogram-dialog`, если flow уже не тривиальный.

Минимальная доменная поддержка:

- Добавь небольшой focused module для admin facade business logic, не разбрасывай product logic по handler.
- В нём должны быть helpers вроде:
  - ensure_admin_access(...)
  - list_registered_users_for_admin(...)
  - ensure_default_spaces_for_user(...)
  - grant_teacher_role(...)
  - add_user_to_student_workspace(...)
  - maybe ensure_shared_family_workspace(...)
- Не удаляй invite/join.
- Не удаляй существующие команды `/assign`, `/granttopic`, `/teacher_content`.
- Новый фасад должен просто позволять подготовить membership так, чтобы ими можно было пользоваться без invite flow.

Тесты:

- Добавь или обнови только узкие тесты.
- Обязательно покрой:
  - admin access only по захардкоженному user id
  - default bootstrap для нового user
  - назначение teacher role
  - подготовку workspace membership так, чтобы teacher потом мог assign/grant другому участнику без invite/join
- Прогони только релевантные тесты.

Документация:

- Обнови `docs/architecture.md` и `context/current-state.md`, если появляется новый bootstrap/admin path.
- В `docs/module-map.md` добавь или уточни строку для этого admin/access area, если это помогает будущим агентам открывать только нужные файлы.

Важно:

- Не выкидывай текущую сложную модель.
- Не удаляй invite/join.
- Просто добавь возможность временно обходить это через понятный admin facade.
- Решение должно быть минимальным, понятным и пригодным для семейного сценария “я + жена + ребенок” без лишней ручной возни.
